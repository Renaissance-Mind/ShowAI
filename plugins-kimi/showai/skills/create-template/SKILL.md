# 创建模板包

## 模板是什么

模板为一类内容保存可复用的判断方法：读者通常要用它做什么，怎样从请求和材料本身判断读者；这类材料各部分提供什么，怎样核对；怎样从材料的结构推出这一次的呈现顺序；怎样从"读者必须看出什么"推出每一部分的画面。它不是页面骨架、填空表或固定章节清单：应用模板得到空白 Page，页面结构由本次的呈现逻辑与设计稿决定；另一份材料按同一套判断应得到不同的结果。

先查 `catalog_list({kind:"template",projectId})` 是否已有覆盖该场景的模板：已有则以新版本修改，没有才新建。按 [show-document](../show-document/SKILL.md) 系统基线的四个阶段，写出这类内容每次都要做的判断、每次材料的来源与形状、读者任务的通过条件。核对 showai_capabilities.templateWorkflow.protocol 为 showai-template-workflow-v2。用户有成熟实例时先验证实例（读取完整 Page，按 [review-presentation](../review-presentation/SKILL.md) 确认它确实支持读者任务，不把未通过的页面当作范例），再按 [实例提炼](references/template-abstraction.md) 创建；结构已明确时按 [直接创建](references/template-creation.md) 继续。只询问会改变方法的缺项；信息充分时完成可用的包与真实应用验证。template_save 保存到显式指定的 projectId；提升为全局是宿主管理操作，用户要跨项目使用时说明这一步。

## 文件夹与元信息

先读 guide({topic:"templates"}) 的当前格式。模板是一个文件夹：README.md 的严格 JSON frontmatter 加概览正文；guides/ 的四阶段 Markdown 或阶段子目录（主文件 README.md，其余按需细节）；components/ 的可选组件包。元信息包含 format、schemaVersion（当前为 3）、id、name、version、description、scenarios、guides、components。guides 必须声明 intent、material、logic、design，null 表示继承系统指南。系统模板由运行时提供，项目模板不能替换或关闭它。内置的 `paper-explainer` 是按本技能写成的完整示例，用 template_context 与 template_guide 读取它的 README 与四份指南作为参照。

## 怎样写才算教判断

每条规则写成三部分：看什么（判断依据）、怎样决定（推导步骤）、为什么（它解决读者的什么困难，以便不适用时知道可以调整）。

- 具体的主干、幕设计、组件对应只能出现在标为"示例"的段落，并说明它由哪些判断得出。logic 的示例主干和 design 的示例幕各至少两个且结果不同，让读者看到差异来自判断而不是来自模板；只有一份实例时，第二个示例按规则推演另一类材料，并标明是推演而非实测。
- 清单（常见用途、可选环节、组件）标为"常见"或"参考"，写出加入条件或选择条件，允许增减。
- 规则里不出现实例名、具体数字、时间预算；不规定读者是谁，而是教怎样判断读者。
- 组件先讲怎样从画面需求决定复用 → 组合 → 扩展 → 新建，再列目前可参考的组件及内置替代，注明随目录更新。

## README 正文是概览

正文（不含 JSON frontmatter）不超过 4 KiB，依次回答五件事：产出什么（一句话加三四个特点）；整体路线（四个阶段在这类内容上各做什么，连成一段）；典型成品的样子（标"示例"，注明是哪类实例的结果）；指南、示例、组件库三者的关系；适用边界（哪些请求不用这个模板）。不要把正文写成指南目录或注意事项清单。

scenarios 写情境，不写做法或特征：请求的形式（给了什么材料、要什么产出）、读者要用结果做什么、重复出现的条件。目录按它匹配请求，所以每条都应是"用户会这样提出"的描述；不把读者身份定死。

## 各阶段指南写什么

- intent：从请求的线索推深层需求的方法，以及深层需求怎样移动重心；从材料本身判断读者已会什么、必须补什么；这类材料的误解来源及其结构特征；可检验目标怎样从材料的主张推出。
- material：材料各部分提供什么与常见陷阱；每条记录的字段；分类或核对的判断依据；贯穿例子、术语、图像怎样记；缺口怎样处理。通用场景可为 null。
- logic：从检验任务与贡献结构推主干；按材料类型选起点形态；组织原则及其理由；可选环节的加入条件；第二级按环节类型该问的问题；先备、通过与停止条件；示例主干。
- design：整体布局怎样定（首屏由什么决定、阅读流、角色色、文字模式及理由）；"读者必须看出什么 → 用什么表达 → 需要什么交互 → 静态与窄屏保留什么"的推导表；组件决策顺序；参考组件清单；每幕要求；至少两幕不同任务的示例幕。

指南是方法与判断标准，不复制系统基线，也不为填满目录增加内容。

## 组件库

模板组件沿 [create-component](../create-component/SKILL.md) 的组件包规范：manifest、props.schema、入口源码与可选 files/assets，加版本化 documentation（使用与开发说明）；默认数据给真实的空态。README 声明本地 id/path，manifest.id 与本地 id 一致；注册时自动加模板命名空间，页面与后续查询使用回执中的精确引用。本地依赖声明本地 id/version；外部依赖仍需精确指纹。组件代码改变时升级组件版本，指南或包结构改变时升级模板版本。design 指南用本地名引用组件，并为没有组件库的使用者给出内置替代。

## 保存与验证

本机和网页 MCP 都用 template_save({projectId,input:{bundle:{format:1,files,assets?}}})：files 以相对路径映射 UTF-8 文本，assets 保存组件图像/字体的 base64；网页端不传本机目录。CLI `template import/export` 属于宿主管理接口。旧的六阶段 schemaVersion 1–2 包仍可读取；新建采用 schemaVersion 3。

保存后用 template_context 取得固定引用与组件索引，按阶段读 template_guide，用一份与示例不同的材料走完四个阶段并 template_apply 制作实例。交付前逐项检查：得到的主干与画面是否不同于示例且合理；规则里有没有实例名、具体数字、时间预算或必选组件；示例是否标注；scenarios 是否是情境；README 是否是概览。修改方法发布新版本，本次事实修订只改实例；原实例保持原样。交付元信息、精确引用、阶段与组件说明、应用 Page 和完整交付文件。
