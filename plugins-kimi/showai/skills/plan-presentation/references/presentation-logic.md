# 呈现逻辑

呈现逻辑决定讲什么、按什么顺序讲、每一部分讲到多深。从读者当下的认知出发构建多级规划；设计稿阶段再为每个节点决定画面。概念之间允许多父关系，阅读路径是一棵深度不同的树，一个节点可以跨多个画面。章节深度不自动决定折叠层级。

## 材料底稿（material 阶段的记录）

重要主张记录来源及具体位置、事件或测量日期、条件、能支持的范围和不确定性。区分事实、作者主张、分析推断、设计建议和生成示意。材料冲突时说明口径与条件差异，不以平均或多数票消除冲突。

论文按任务、方法、设置、证据和局限核实；数据分析核对粒度、单位、样本和计算；教程核对实际入口、版本、操作与反馈。通用任务没有专门采集流程时保留这项轻量的来源与支持范围检查即可。停止收集的条件是材料足以回答主要问题、支撑关键判断并说明重要限制。时间范围延伸到当下时以真实检索日为界。

## 第一级：整体逻辑与环节主题

先选整体逻辑：理解方法、研究或论证用“背景与动机 → 问题 → 机制 → 证据 → 条件与局限 → 自测”；理解概念或系统用“具体问题 → 对象与关系总览 → 关键过程 → 例子与反例 → 适用边界”；作出选择用“目标与标准 → 候选与可比事实 → 差异 → 取舍与条件”；完成操作用“前提与结果 → 步骤 → 反馈 → 异常与恢复”；了解进展用“截止时间与结论 → 变化 → 依据 → 风险 → 待决策事项”。模板 logic 指南会给出该类内容的主干与可选环节。

每个环节写一句主题：读者读完这一段应当知道什么。第一级的顺序层层递进：每个环节只依赖前面已经讲过的内容。读者需要先了解背景才能看懂结论时（讲解论文、方法、研究或陌生概念），从任务背景与动机开始，不在开头放读者此时看不懂的总结或结论；只有读者已经掌握背景、只缺结论时（进展汇报、事实查询、标准已明确的选择），才把结论放在最前。背景只讲后文需要的部分。

## 第二级与继续细化

| 字段 | 判断标准 |
| --- | --- |
| task 读者任务 | 这一部分读完能解释或完成哪件事 |
| answer 核心回答 | 一句明确的结论或关系 |
| needs 先备条件 | 需要哪些节点；缺少时在哪里补充 |
| children / explanation | 下一级节点；叶子写准备讲清的定义、过程、例子、反例、证据与边界 |
| check 通过条件 | 用什么复述、判断或操作检查理解 |

为每个主题列出讲清它所需的内容；按读者简报判断哪些已知（直接使用）、哪些要解释（展开）、哪些要先澄清（提前）。对仍难理解的概念或关系继续展开，直到叶子写出具体内容；只写“介绍某概念”不算展开。每个分支在读者能完成对应任务时停止，深度可以不同。共享概念只定义一次，在使用处短释并定位。改变结论或操作正确性的条件必须在主线可见。熟悉主题的读者可以从差异和证据直接进入，为他们标出入口。

展开每一层时问三个问题：这一部分符合读者当前的认知吗；读者能据此理解吗；还需要进一步解释吗。回答“否”的部分调整顺序、补先备概念或增加例子。

## 填写示例

主题：如何为比较材料选择模板。

- 一级：确定阅读任务；检查结构是否合适；验证真实内容。
- “结构是否合适”展开为必需材料、阅读顺序、内容密度。
- “必需材料”继续展开为共同标准、可比口径、缺项及其对结论的影响。
- “阅读顺序”用标准 → 差异 → 取舍和一个具体例子即可停止。
- “内容密度”按桌面与窄视口两种布局解释，不要求同样的层数。

该节点的通过条件：读者面对一份材料不齐的比较任务，能说明可采用的结构，并指出暂时不能给出的结论。

## 复杂作品的可检查规划

研究报告、机制讲解和综合方案在制作前把规划保存为工作材料 `presentation-plan.json`。它不是读者正文，也不是 MCP 参数。已有合适规划可续改；简单问答与局部编辑不用创建。

文件记录 reader、startingKnowledge、goal、cutoff（材料检索截止日期）、environment={width,height,interactive}、nodes 和 scenes。nodes 是嵌套数组：每项含稳定 id、task、answer、check，可含 needs（先备节点 id）和 children；叶子另含 explanation。scenes 在设计稿阶段填写，字段见 [设计稿](../../design-presentation/references/design-draft.md#保存设计稿)。

有文件系统的本机宿主把文件写在当前任务工作目录（宿主启动时的工作目录或用户指定的目录）或用户指定位置，不写进内容库、插件目录或展示输出目录，交付时说明实际路径。没有文件系统的授权网页宿主，把同一 JSON 保存为目标项目内独立的“工作材料：呈现规划”Page（文本或代码内容），保留它的 Page ID，与成品分别维护。仅有匿名独立渲染能力时交付可下载的完整规划文本并说明未保存到项目。

设计稿完成、首次填入完整页面内容之前，运行 `python3 <plan-presentation目录>/scripts/check_plan.py <规划路径>`；从 show-document 或 review-presentation 进入时同样使用本技能目录下的脚本，直接执行即可。处理失联节点、缺少解释、依赖循环和无画面覆盖等错误，再用设计判断检查展开是否足够。校验返回的哈希用于对应本轮规划；通过仅证明结构可追踪，不证明内容正确或设计优秀。宿主不能运行脚本时手工核对同样关系并说明范围。交付前的最终映射用 `--page` 另行校验，见 [评审标准](../../review-presentation/references/review-criteria.md)。制作中改变主线或画面时同步更新规划；保留最初规划和修订原因。

多个作品分别确定认知缺口和讲解顺序，可以共用来源与组件，不把一份通用规划批量换标题后作为不同作品的规划。
