# 呈现工作约定

围绕读者的实际任务组织内容。完整作品依次形成四份记录——读者简报、材料底稿、呈现规划、设计稿——再据此制作源页面并评审。简单任务可以把判断合并写在对话里；已完成且仍有效的记录直接复用，阶段交接不要求用户逐次确认。

## 读者简报

| 项目               | 需要明确的内容                                                       |
| ------------------ | -------------------------------------------------------------------- |
| 表面要求与深层需求 | 用户原话要求什么；读者拿到内容后要做什么判断、决定或操作；推断的依据 |
| 读者与认知起点     | 谁阅读；已经理解什么；缺少什么（在哪一步补）；可能的误解及是否先澄清 |
| 目标结果           | 读者看完后能解释、判断或完成什么；用什么任务检验                     |
| 范围与材料         | 必须覆盖、可省略、来源、缺口；推断出来的部分标为假设                 |
| 环境               | 设备、实际视口、阅读时间、交互能力、静态或离线交付                   |
| 约束               | 用户指定的格式、素材、模板、入口与保存归属                           |

没有特殊要求时以电脑全屏可交互阅读为设计参考（1440×900 CSS 像素）；实际宿主可能是窄面板，交付前核对视口。不要把显示器分辩率直接当作 CSS 视口，也不要把长文统一压成固定比例画布。

## 阶段交接

| 环节           | 记录                 | 进入下一步的条件                                                         |
| -------------- | -------------------- | ------------------------------------------------------------------------ |
| 理解意图       | 读者简报             | 目标可检验；影响结果的未知条件已处理或标明；知道要先澄清哪些误解         |
| 收集与处理材料 | 材料底稿             | 关键主张有依据与条件；结论范围不超过材料；缺口已记录                     |
| 呈现逻辑       | 多级呈现规划         | 主线连贯；需要解释的概念都有落点；各分支深度适合读者；每个节点有通过条件 |
| 呈现设计稿     | 逐幕设计稿           | 每个节点有具体画面；画面具体到另一位制作者能画出来；素材与现有能力可支撑 |
| 制作           | 源页面与 blockIds    | 真实内容与设计稿一致；缺项和限制可识别                                   |
| 评审交付       | 问题、修订与验证范围 | 主要任务可完成；保存、导出和显示各有对应证据                             |

发现问题时回到负责它的阶段：错读数据回材料；缺少先备概念回呈现逻辑；标签难读或选择后无反馈回设计稿。

## 记录与权限

复杂任务保留简洁的目标、证据、关键设计选择和未覆盖项，便于续改。用户只要求规划或设计时交付相应记录；用户要求成品时继续完成成品。最终正文保留读者需要的方法和限制，制作过程记录放在工作材料中。

这些是记录的内容约定，不是新的 API 或自动参数绑定系统。简单问答、用法和仅在对话中讨论提纲时直接回答。用户要求完整规划、设计稿或报告等可审阅成果时，默认按已核实的项目归属保存正式 Page 并展示；用户明确只在对话中讨论、只要文件或不入库时，遵循指定方式。“先设计、不实现”限制的是后续应用或组件实现，不改变记录的保存归属。

当前连接与项目已核实就继续操作。首次接入、换项目或归属不明时使用 [use-showai](../../use-showai/SKILL.md)。截图只证明相应视图；交互检查与真实读者试读分别记录，遵循宿主的电脑操控规则。
