# 从成熟实例提炼模板

先读取完整原 Page、hash/revision 与精确组件引用，并取得它的读者简报、呈现规划与设计稿（没有记录时从页面反推并标明）。有两份以上实例时都读；一份实例只能说明一种结果，两份才能看出哪些是判断、哪些是巧合。

## 把实例拆成判断与结果

对实例中的每个决定（为什么首屏放这些、为什么先讲问题、为什么这一段用这种画面、为什么这个环节存在）问两个问题：是哪些判断得出了它；换一份材料这个判断会不会得出不同结果。会的，把判断写进指南，把结果写进"示例"；不会的，它是这类内容的共性，写进规则并说明理由。本次发现、日期、数值、贯穿例子、素材来源、实例名都属于实例，只在示例段落以描述方式出现，不进入规则。不要复制截图或章节名称当作结构。

## 按文件夹格式写入

按 [create-template](../SKILL.md) 的格式提炼。README 正文写概览（产出什么、整体路线、典型成品示例、指南与组件的关系、边界）；scenarios 写用户会怎样提出这类请求。guides/ 按四阶段分别保存：intent 写从请求和材料推读者的方法、误解来源、目标怎样从主张推出；material 写材料各部分提供什么、记录字段、分类判断依据；logic 写从任务与结构推主干、按类型选起点、组织原则及理由、可选环节的条件、第二级该问的问题，附至少两个结果不同的示例主干；design 写整体布局怎样定、"必须看出什么 → 表达 → 交互 → 静态"的推导表、组件决策顺序、参考组件清单、每幕要求，附示例幕。系统已经规定的共性直接继承。

## 组件

抽取组件前检查是否需要复用代码。仅改输入/布局够用时沿用公共能力；确实有这类内容反复需要的图形或交互才放入 components/。该库使用本地 ID、真实 schema、默认空状态和版本化使用/开发说明；注册器生成实际引用，不能写死另一个项目的路径或指纹。只属于某一篇材料的机制组件不进模板，在 design 指南中说明何时按 create-component 新建。

## 验证

保留原实例。新包保存后，以另一份材料走完四个阶段并应用，检查得到的主干与画面是否不同于示例且合理；某条规则只对原实例成立时，改为示例或加上条件。再检查规则里有没有实例名、具体数字、时间预算、必选组件。材料不足时交付可用方法和未验证范围，不编造实测结论。后续修改发布新模板版本；组件代码改变也升级组件版本。
