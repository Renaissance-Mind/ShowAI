# 创作与修改作品

这份 Skill 是制作作品的完整流程，开头一次读完，不用再读其他流程 Skill。还没读过 [use-showai](../use-showai/SKILL.md) 时先读它，核对连接、项目归属和保存规则。用户只要对话讨论时直接回答；只想在对话里看一两个图表、示意或模拟时用 [show-visual](../show-visual/SKILL.md)。用户只要规划或设计稿时，做到相应环节为止，不实现成品：记录照常写进记录文件夹（presentation-plan.json 顶层写 title，以后没有 pageId 也能按标题找到），在对话里给出读者简报、规划与设计稿的可读版本，并告诉用户记录文件夹的位置；之后要实现时沿用这份记录。用户要求评审已有页面时，读回页面后直接进入评审环节。

用户要求翻译、转述或整理一篇原文时，保持原文的顺序与完整内容并注明出处；补充的解读另行标注（例如组件标题以「解读」开头），不改写原文结构；原文顺序优先于设计稿中关于章节编排的建议，各环节的判断用于决定在哪里补充解读。

## 系统呈现规则

目的是让读者理解内容、完成自己的任务，而不是把材料搬上页面。从读者的认知和真实需求出发，经过材料处理、呈现逻辑规划和视觉设计，形成易于理解、能支持读者任务的作品。

一份作品依次经过七个环节。每个环节交出一份记录，下一个环节以它为依据：

1. **理解意图**：读者实际想知道什么，已经知道、缺少、可能误解什么。交出读者简报。
2. **收集材料**：需要哪些事实与数字，各自的来源、条件和性质。交出材料底稿；通用场景可以省略这一环。
3. **呈现逻辑**：从读者当下的认知出发做多级规划，决定讲什么、按什么顺序、讲到多深。交出呈现规划。
4. **设计稿**：确定环境、整体布局，以及每一部分的画面、文字落点和交互。交出逐幕设计稿。
5. **制作**：按设计稿逐幕写入页面。
6. **评审**：对照读者简报和设计稿检查真实页面并修订。交出评审记录。
7. **交付**：把页面交给读者，说明位置和未验证的部分。

简单任务可以把几份记录合并写短，但不跳过判断。选用模板时，模板为这类内容补充各环节的具体方法；本规则始终生效，模板不能关闭它。

### 视觉表达原则

- **整体与局部都要设计。** 既考虑整份内容的布局与阅读流，也考虑每一部分怎样呈现。
- **优先用图表达。** 过程、机制、结构、空间关系和方案对比以图为主；只用段落或表格讲这几类内容，读者要在脑中自己搭画面。图片可来自真实素材，也可用图像生成制作。
- **机制图画出状态。** 对象持有的表、携带的地址、此刻的值都放进画面，变化处突出；有先后的机制按步骤展示，各步沿用同一布局，只改变这一步变化的部分。
- **文字补足图。** 图中没讲清的概念、条件和细节用文字说明；文字与相邻的图使用同一对象名称与数值，读者看得出两者对应。
- **文字排布保证可读。** 用加粗、颜色区分重点与层级，同类含义用同一种样式。

## 环节一：理解意图

这一环节回答：读者实际想知道什么，要让读者理解它，先得补上什么。

**判断真实需求。** 先写下表面要求：用户原话要什么形式、什么范围。再结合对话上下文、材料和场景推断深层需求：读者拿到内容后要做什么判断、决定或操作，为什么现在需要。写明推断依据。两者不一致时按深层需求组织内容，同时把用户明确问到的内容放在显眼位置回答。只有题目时按最合理的读者与用途假设推进，并标为假设；只有不同理解会做出完全不同的作品时才向用户提问。

**判断读者认知。** 读者是谁、为什么读；哪些概念和事实可以直接使用；理解结论前必须补上哪些知识，各在哪一步补；可能有哪些误解。会影响后续理解的误解先澄清：先给出可核实的定义、例子或反例，再展开原来的问题。不影响主线的误解在相应位置顺带说明。

**任务结果与环境。** 写出读者看完后能解释、判断或完成的事情，并给出检验方式，例如“能说出 A 为什么比 B 快，并指出前提条件”。这些检验在呈现逻辑里变成各部分的通过条件，评审时逐项核对。记录环境与约束：设备与实际视口、是否可交互、是否要静态或打印版本、阅读时间、用户指定的素材、模板、格式与保存归属。没有特殊要求时按电脑全屏、可交互阅读设计。

**读者简报**包含：表面要求与深层需求、读者与认知起点（已知、缺少、误解）、可检验的目标、范围与假设、环境与约束。目标可检验、影响结果的未知条件已处理或标明、知道要先澄清哪些误解时，进入下一环节。

## 环节二：收集材料

这一环节为呈现准备可靠的内容基础。后面的呈现逻辑只使用材料底稿中有依据的内容。

**何时可以省略。** 解释常识性概念、整理用户已经给出的完整材料这类通用场景，没有统一的采集方式，可以省略这一环节；要用到的事实仍做一次来源与条件检查。模板为特定内容规定了采集清单时，按清单执行。

**确定需要什么。** 从读者简报倒推：每个要作出的判断需要哪些事实、数字、例子、图像或原文；每个要澄清的误解需要哪个定义或反例。再决定来源：用户材料、原始文献或数据、官方文档、检索结果、真实截图。优先原始来源，不依赖二手摘要。

**核对与整理。** 材料底稿按条目记录：主张或数据（原文或原值）、来源定位（文件、页码、表号、链接或命令输出）、条件（前提、口径、单位、样本、日期、对照对象）、性质（事实、作者主张、他人评价、分析推断、设计建议、生成示意）、用途（支持哪个结论或解释哪个概念）。材料之间冲突时记录口径与条件的差异，不用平均或多数票消除；不同口径的数字不并列比较。缺少决定性材料时继续查找或缩小结论范围，不为填满结构编造数据或例子。准备生成示意图时，先写下必须保持准确的对象、数量、关系与标签。

**何时停止。** 材料足以回答读者的主要问题、支撑关键判断并说明重要限制时停止。时间范围延伸到当下的主题以实际检索日为界。真实缺口写进底稿，它们会成为作品中明确的限制。

## 环节三：呈现逻辑

这一环节决定讲什么、按什么顺序讲、每一部分讲到多深。从读者当下的认知出发做多级规划；设计稿再为每一部分决定画面。

**第一级：整体逻辑与环节主题。** 先选整体逻辑，再给每个环节写一句主题，说明读者读完这一段应当知道什么。常见逻辑：

| 读者任务 | 整体逻辑 |
| --- | --- |
| 理解一个方法、研究或论证 | 背景与动机 → 问题 → 机制 → 证据 → 条件与局限 |
| 理解一个概念或系统 | 具体问题 → 对象与关系总览 → 关键过程 → 例子与反例 → 适用边界 |
| 作出选择 | 目标与标准 → 候选与可比事实 → 差异 → 取舍与条件 |
| 完成操作 | 前提与结果 → 步骤 → 预期反馈 → 异常与恢复 |
| 了解进展或现状 | 截止时间与结论 → 变化 → 依据 → 风险 → 待决策事项 |

顺序层层递进：每个环节只依赖前面讲过的内容，读者不会遇到还没解释的结论、概念或数字。读者需要先了解背景才能看懂结论时（讲解论文、方法、陌生概念），从任务背景与动机开始，不在开头放读者此时看不懂的总结；只有读者已经掌握背景、只缺结论时（进展汇报、事实查询），才把结论放在最前。背景只讲后文需要的部分。

**第二级与继续细化。** 为每个主题列出讲清它所需的内容：定义、对象及关系、过程、例子、反例、证据、成立条件。按读者简报判断哪些已知（直接使用）、哪些要解释（展开）、哪些要先澄清（提前）。仍难理解的部分继续展开，直到叶子写出具体的定义、过程、例子或条件；只写“介绍某概念”不算展开。各分支在读者能完成对应任务时停止，深度可以不同。共享的概念只解释一次，在使用处短释并指回原处。改变结论或操作正确性的条件必须在主线中可见，不能只放进折叠或悬停说明。

展开每一层时问三个问题：符合读者当前的认知吗；读者能据此理解吗；还需要进一步解释吗。回答“否”的部分调整顺序、补先备概念或增加例子。

**呈现规划的记录。** 规划是一棵节点树，每个节点写：id（稳定标识）、task（读完能解释或完成什么）、answer（一句核心回答）、needs（先备节点的 id）、children（下一级），叶子另写 explanation（准备讲清的内容），每个节点写 check（评审时读者应能完成的复述、判断或操作）。

**常见问题。** 先写完整长文再给每章配一张概括图；开头放读者还看不懂的结论或数字；后文才解释的概念提前出现；用抽象名词框图代替机制解释；关键条件只出现在脚注。发现这些问题时回到规划修改，不在设计稿里补救。

## 环节四：设计稿

这一环节把呈现规划变成具体画面。设计稿是制作的唯一依据，要具体到画面里有什么、怎样组织、彼此关系，详细程度接近图像生成的文本指令，另一位制作者能据此做出同一画面。

**环境。** 记录分辨率、长宽比和是否可交互。没有特殊要求时按电脑全屏、可交互阅读设计，参考视口 1440×900 CSS 像素；实际宿主可能更窄，交付前核对。演示画面可用 16:9，长文自然纵向排布。需要静态导出或打印时，为每个交互部分设计静态替代。

**整体布局。**
- 首屏在参考视口内不滚动就能看出这份内容从什么问题讲起、范围是什么，并有一幅看得懂的画面；读者需要先了解背景时，首屏就是背景与动机的第一幕。不重复页面标题。
- 图文相邻：每一部分的说明放在它解释的图旁边，不先铺几段背景再放一张图。
- 节奏：长章节按理解节点拆成图文相邻的片段，避免一两个交互区后接几大块连续正文。
- 对象身份稳定：同一对象在各部分使用同一名称、颜色、形状与位置，具体值在各图和正文中一致；后一张图沿用前一张的对象与布局，只改变要讲的部分。
- 窄视口重排图文和导航。

**每一部分的表达。** 先写下读者要看出的关系，再判断能不能画出来，然后按读者任务选形式：

| 读者任务 | 优先形式 |
| --- | --- |
| 认识对象与组成 | 原图、截图、剖面或标注示意，选择局部时就近解释 |
| 理解步骤与状态变化 | 流程、连续分镜、前后状态，对象身份保持 |
| 理解机制 | 输入—作用—结果的关系图，画出状态；可操作的参数让读者预测变化 |
| 比较与取舍 | 对照表、同尺度小多图、决策路径；共同口径，缺项可见 |
| 趋势、分布与异常 | 与数据语义匹配的图表；单位、样本、日期、原始值与来源 |
| 完成操作与排错 | 真实界面标注、步骤与分支；动作、反馈与恢复方式 |
| 核对论证或精确规定 | 有层次的正文、公式和原文；条件突出，图文相邻 |

表格适合查阅类信息，例如命令、参数、价格和功能清单。图形的方向、空间、连接和尺度承担语义，装饰不能暗示没有证据支持的因果、比例或排名。

**文字。** 标题直述主题；导语说明接下来看什么、用哪个例子、怎样操作；图注解释图中没讲清的概念；要点说明看完应能回答什么。动笔前先定下几种含义各用什么样式，例如结论加粗、需要对照的数字高亮、术语首次出现加悬停注释，全文一致。读者可能不认识、但不值得打断正文的实体（公式变量、缩写、专有名词）用悬停注释说明；主线必需的定义和改变结论的条件写在正文。桌面正文 18–20 px 起，空间不足时改结构，不缩小字号。

**交互。** 写清初始状态、触发动作、状态变化、可见反馈与恢复方式。默认状态是材料中的真实设定；交互只改变阅读焦点或临时参数，不改写事实。静态替代保留主线、关键状态与完整图注。

**组件与素材。** 先定表达形式，再查真实能力：组件索引用 project_context 返回的 componentCatalog（或 `catalog_list({kind:"component",projectId})`），模板组件来自 template_context。选用后读精确版本的 guide 与 parameters。顺序是：调整已有组件的数据与布局 → 组合已有能力 → 扩展已有组件 → 为确认的缺口新建组件（create-component）。常用对应：
- 流程与分支用 flowchart；参与者之间按顺序的往返用 sequence-diagram；分层架构用 layer-diagram。
- “谁持有什么、这一步改了什么”的机制（网络包、缓存、事务、握手）用 mechanism-diagram：对象可带小表格，steps 只写每一步的变化，同一布局逐步切换。各步画面本身不同时用 stepper，每一步放一张图或一个组件。
- 没有现成组件的示意图（同尺度小多图、分层平面、空间示意）用 svg 手绘；几个方案并排对比时画在同一张 svg 里。
- 数据用 chart 或适配数据类型的 G2 图表；对照用 table、comparison-matrix；参数探索用 playground；操作步骤用 step-guide；目录或字段结构用 structure-browser。
- 主题页、人物页、项目页需要汇总“哪些页面提到了这里”时放 backlinks；句子里的日期写成 date（Markdown `@[date]{"date":"2026-11-20"}`），提到另一页时写页面链接。
- 真实图片记录来源；生成图先写下必须保持准确的对象、数量与标签，生成后核对，精确数据与可操作对象保留为原生组件。

**设计稿的记录。** 每一部分写一幕（scene）：id、nodes（它解释的规划节点）、form（表达形式与所选组件）、composition（画面中的对象、相对位置、箭头或尺度、准确标签、颜色、阅读顺序与文字落点）、visualReason（为什么这种表达支持当前任务）、text（导语、图注、要点及其样式）、interaction（trigger、change、reset，没有交互时省略）、static 与 narrow（静态导出和窄于 640 px 时怎样呈现）、assets（素材来源或生成提示）、check（读者看完这一幕应能完成什么）。“文字加关系图”“白底简洁”不能单独成为 composition。

示例：暖白底，标题“同一个问题，两种输入布局”。上行是生成式模型的序列：[视频][问题] 后接逐个生成的时间 token，灰色箭头表示逐步输出；下行是打分式模型：[视频][指令+问题][候选…][decide]，候选段用橙色，共享的视频段标“共享”。点击任一片段时，下方说明区显示该片段的作用，其他片段降低饱和度；再次点击恢复。图注解释“共享”意味着只计算一次。窄屏时两行上下堆叠并允许横向滚动。

## 环节五至七：制作、评审与交付

**制作。** 制作只做一件事：把设计稿落实为页面。按幕的顺序填入真实内容：导语、图形或组件、图注与要点；文字样式按设计稿定下的方案使用。每幕完成后记下实现它的块 ID（blockIds），填回设计稿。制作中发现设计稿行不通时，先改设计稿，并写下原因，再继续制作。

**评审。** 对照读者简报和设计稿检查真实页面，不凭记忆判断。截图按设计稿记录的视口（默认 1440×900）显式指定，再看窄于 640 px 的视口。先看首屏，再看最复杂的机制和比较区域，逐项核对：

- 意图：回答了用户问到的内容，深层需求得到支持，误解在影响理解之前澄清。
- 材料：数字、单位、日期、条件和来源一致，派生值与原值一致。
- 逻辑：核心关系可以复述，需要解释的概念都有落点，关键条件在主线可见。
- 视觉：过程、机制、结构与对比以图为主；机制图画出状态；图中对象、关系和标签与设计稿一致；实际视口中标签清楚。
- 文字：图中没讲清的有文字补足；文字与相邻的图名称和数值对得上；样式含义一致。
- 交互：操作有反馈、可恢复，默认状态等于材料设定；键盘与窄屏可用；读者视图中没有编辑表单、内部类型名或字段名。

问题写清位置、实际观察、对读者的影响和修改方向，回到负责它的环节修改：数据或条件问题回材料，缺少先备概念回呈现逻辑，表达或状态问题回设计稿。严重问题（错误事实、缺少决定性证据、条件被隐藏、主要操作无法完成）优先处理。截图证明视图，实际操作证明那条路径的行为，只有目标读者试读才能证明理解效果；没有执行的检查明确标为未验证。

**交付。** 新作品保存后展示给用户，并说明它存在哪个项目、怎样打开。续改已有作品在原页面上完成，默认告诉用户改了什么、页面在哪里，用户要求时再展示。交付时说明未验证的部分；没有真人试读不声称已证明理解效果。

## 用 ShowAI 完成各环节

### 开始

核对 `showai_capabilities.templateWorkflow.protocol` 为 `showai-template-workflow-v3`。老运行时返回 v2 时，template_context 只给出模板的 README，改用它提供的 `template_guide` 按阶段读取模板指南，并告诉用户运行时需要更新；不能声称仅安装 Skill 就升级了工具。

新作品先按 use-showai 确定项目；只要规划或设计稿时也先确定项目，查模板需要它。续改已有作品时先 `page_read({projectId,pageId,rendered:false,response:"source"})` 读回原 Page，取它的 `templateContext`（源超过 256 KiB 的大页这样读只返回大纲窗口，要取 templateContext 时加 `detail:"full"`，本机连接也可用 `out` 写入文件再读），并在记录目录中查找 presentation-plan.json 里写有这个 pageId 的记录；找到就沿用其中的读者简报、规划和设计稿，只重做受影响的部分；找不到时从页面本身和用户说明反推，新建一个记录文件夹：brief.md 标明内容是反推的，presentation-plan.json 只为本次要改的部分写节点和幕（含现有块的 blockIds），check_plan 与评审以这部分为准。

**查模板。** 每个新作品在理解意图之前调用一次 `catalog_list({kind:"template",projectId})`，按用户的请求和手上材料的类型（例如给了一篇论文）对照各模板的 scenarios，判断是否适用；选中的模板从第一个环节起就补充方法。用户指定模板时直接使用。用户要求空白，或没有合适的模板时，只按上面的流程制作，用 page_create 建页；需要查看模板上下文时 `template_context` 传 `templates:[]`，它会覆盖连接启动时带的默认模板。续改沿用 Page.templateContext 记下的精确版本，没有记录时不猜它原先用过哪个模板。内置模板升级后旧版本不再随运行时提供，按记下的版本读取报找不到时，改用同一模板的当前版本，并告诉用户模板版本变了。

**读模板。** 选定模板后调用一次 `template_context({projectId,templates})`，它返回每个所选模板的 README、全部指南和组件索引（组件多时按 componentPage 分页）。一次读完，然后在每个环节把模板对这类内容的方法叠加在默认做法上；模板没有写到的环节按默认做法。保留返回的 `context.templates`，建页时使用。

### 记录

每个环节交出的记录写成文件，供续改、评审和提炼模板时使用。`showai_capabilities.authoring.workRecords.available` 为 true 时，记录目录是它返回的 directory：默认在系统临时目录，用户可以在「设置 → 通用」改成固定目录。每份作品新建一个文件夹 `<directory>/<YYYYMMDD-HHmm>-<作品短名>-<8 位随机十六进制>/`，随机部分保证每次都不同。文件夹里放：

- `brief.md`：读者简报。
- `material.md`：材料底稿，省略材料环节时不建。
- `presentation-plan.json`：顶层写 reader、startingKnowledge、goal（各一句，详细内容在 brief.md）、cutoff（材料检索截止日期；省略材料环节时写当天日期）、environment `{width,height,interactive}`、nodes（呈现规划）和 scenes（设计稿）；每个节点（包括上级节点）都要出现在某一幕的 nodes 里。建页后补上 projectId 与 pageId，制作后为各幕填入 blockIds。
- `review.md`：评审发现、修订与未验证项；以后续改时在末尾追加。

设计稿完成、第一次写入页面之前，运行 `python3 <本 Skill 目录>/scripts/check_plan.py <规划路径>` 检查规划与设计稿的结构覆盖。评审时把 `page_read({response:"source"})` 的完整结果存进同一文件夹，再加 `--page <页面源>` 检查各幕的 blockIds。宿主不能运行脚本时手工核对同样的关系并说明。脚本只检查结构，不证明内容讲清楚了。

`workRecords.available` 为 false 时（例如远程连接）不落盘，记录写在对话里，交付时说明。几句话就能写完的简单任务，可以只写一个 brief.md 或写在对话里。只改一两处措辞、数字或样式的局部小改不新建记录，有原记录时在它的 review.md 追加一行；改动涉及讲解顺序、增删部分或重做画面时按续改处理。记录是这台设备上的工作材料，不随页面同步或导出；交付时告诉用户记录文件夹的位置。

### 制作与交付

用了模板时用 `template_apply` 建页，它生成空白 Page 并记住模板引用；不用模板时用 `page_create`，只传标题和少量块，再用 `page_apply` 逐幕插入。插入组件、文字标记、图片、链接、修改已有页面的具体写法见 [写入页面的操作](../use-showai/references/authoring.md)；组件的 guide 与参数在选用时读取。设计稿确认的组件缺口进入 [create-component](../create-component/SKILL.md)，完成后回到这里继续制作。要嵌入较多图片或视频时，设计阶段先按 [容量与大文件](../use-showai/references/capacity.md) 决定用引用还是嵌入。

新作品保存后调用 `page_present`，并先读 [当前宿主适配](../use-showai/references/host-adapter.md)，在同一轮把页面展示给用户；告诉用户页面存在哪个项目，给出 openUrl。续改已有作品时在原页面上修改，保存后默认不再展示，告诉用户改了什么、页面在哪；用户要求查看效果时再展示。导出文件、多页网站和本机文件打包的做法见 [写入页面的操作](../use-showai/references/authoring.md#展示与导出)。

## 从对话展示升级

用户在 [show-visual](../show-visual/SKILL.md) 展示之后只想保存那几个组件时，按 show-visual 的“之后要保存”原样写入，不必走制作流程。要把多次展示整理成一份有结构的文档时，从理解意图开始走完整流程，已有展示的数据作为材料，组件按设计稿取舍。
