# Contributing a built-in component

**Language:** English | [简体中文](i18n/contributing-components.zh-CN.md) · [Documentation](README.md) · [Contributing](../CONTRIBUTING.md)

A built-in component ships inside every ShowAI runtime: the desktop and browser workbenches, the CLI and MCP server, the offline reader in exported pages and the CDN reader. Agents find it through `catalog_list` without installing anything, and pages store only its data. This guide walks through adding one and changing an existing one.

## Built-in or project component

Most reusable components should start as project components. An Agent with the ShowAI plugin creates them through the `create-component` Skill, they are versioned in the user's content library, and they can be promoted to global scope or published (see [Components and templates](catalog-lifecycle.md)). No change to this repository is needed.

Propose a built-in when the component serves many kinds of content rather than one topic, its data contract is stable, and it has already proved itself as a project component or in real pages. Open a feature request first and agree on the `kind` name, the data it stores and how it relates to existing built-ins. Extending an existing built-in is often better than adding a near duplicate: `stepper` replaced `step-walkthrough`, and `step-walkthrough` now stays only for existing pages.

The folders in `resources/catalog/task-gantt`, `value-slider` and `text-diagram` are importable component packages used as examples and test fixtures. They are not built-ins and are not registered automatically.

## How a built-in fits together

A typical built-in is a React block. Its data is a JSON object stored in the page; the block renders it, edits it through `onChange`, and respects `readOnly` in reading views and exports. Four pieces describe it:

| Piece         | Where                                                    | Used by                                                                           |
| ------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Data contract | `src/components/blocks/<name>-contract.mjs` and `.d.mts` | Workbench, CLI and MCP saves, document validation and the portable reader         |
| Renderer      | `src/components/blocks/<Name>.tsx` and `<name>.css`      | Workbench, readers and the editable SDK copy                                      |
| Catalog entry | `resources/catalog/components.json`                      | Registry defaults, `catalog_list`, Ajv validation of `propsSchema` and examples   |
| Documentation | `resources/catalog/component-documentation.json`         | `catalog_describe` guide and parameter views that Agents read before writing data |

The contract is a dependency-free validator that throws errors naming the exact field path, for example `items[3].depends[0]`. It runs in places without React or a bundler, so it imports nothing. `propsSchema` describes the same data for Agents and Ajv; keep the two consistent.

G2 charts and the external diagram families follow their own pipelines. G2 entries in `g2.json` and their exports are generated by `node scripts/generate-g2-components.mjs` from `src/components/blocks/g2/`; their documentation entries are written by hand. Diagram families use `diagrams.json`, `diagram-documentation.json` and `src/components/blocks/diagrams/`; see [Diagram components](diagram-components.md). Primitives such as `text`, `table` and `stepper` live in `primitives.json` and `Primitives.tsx` and are rarely added.

## Adding a block

The steps below follow what recent additions such as `scene-3d` and `roadmap` touched. `src/components/builtin-registration.test.ts` checks the registration points marked with ✓ and fails with the missing kinds.

1. **Contract.** Write a contract module with an exported validator and a `.d.mts` declaring its types, for example `scene3d-contract.mjs` with `validateScene3dData(data)`. Related components may share one module: `roadmap` and `waterfall` both use `validatePlanData(kind, data)` from `plan-contract.mjs`. Reject unknown shapes with field paths, bound every list and string, and test the defaults, the examples and the rejected shapes next to the contract (`scene3d.test.ts`, `plan.test.ts`).
2. **Renderer.** Write `<Name>.tsx` taking `BlockProps` (`data`, `onChange`, `readOnly`) and its stylesheet. Put every UI string in a message namespace `src/i18n/messages/<namespace>.ts` with both `zh-CN` and `en`; `src/i18n/i18n.test.ts` rejects hard-coded Chinese and mismatched keys. Use the shared selection, context and hover menus of the host editor instead of adding a floating toolbar.
3. **Catalog entry ✓.** Add an object to `components.json` with `kind`, `name`, `description`, `scenarios`, `defaultData`, `propsSchema`, `examples` (each `{ name, request, data }`), `version` (semver, start at `1.0.0`) and `effects`. The catalog keeps Chinese names and descriptions because Agents and the CLI read them.
4. **Documentation ✓.** Add an entry keyed by the kind to `component-documentation.json` with `version`, `reuse`, `usage` and `development`; copy the shape of a recent entry such as `roadmap`. Existing built-ins use documentation version 1. Version 2 adds verified parameter meanings and omission rules; see [Component parameters](component-parameters.md).
5. **Registration ✓.** In `src/components/blocks/registry.ts`, add a lazy import and a literal `registerBlock({ kind: "…", … })` that reads `defaultData` from `componentMetadata` and passes the contract as `validate`. The kind must be a string literal: `scripts/build-reader-source.mjs` parses these calls so an exported page bundles only the components it uses.
6. **Document validation.** Import the contract in `src/portable/validation.mjs` and add a `kind === "…"` branch in `validateWidgetData`. Unknown kinds pass without checks, so no test notices a missing branch; review this step by hand.
7. **Editable SDK ✓.** Export the renderer from `src/components/blocks/sdk.tsx`. In `src/core/builtin-sources.ts`, add `?raw` imports of the `.tsx`, `.css`, contract and message files to `sources`, and the export name to `builtinExports`. `npm run check:sdk` and the i18n test fail when a shipped file imports a module that is not shipped.
8. **English display ✓.** Add the English `name` and `description` to `src/components/builtin-display-text.ts`. Without them the English interface shows the Chinese catalog text.
9. **Category ✓.** Add the kind to `builtinCategories` in `src/core/component-categories.ts` so the component browser groups it.
10. **Inline readiness ✓.** Add `{ "status": "ready" }` to `resources/catalog/inline-readiness.json`, or another status with a `note` when the component does not yet work well inside a conversation. Measure it with the readiness run below.
11. **Hard-coded lists.** Add the kind to the ordered list in `src/core/catalog.test.ts` (`describes all built-in blocks for agents`) and, when the offline reader should mount it, to `src/agent/presentation-export.test.ts`.
12. **Runtime dependencies.** A new npm dependency used at runtime goes into `package.json`, the copy list in `scripts/package-runtime.mjs`, the runtime and SDK import allowlists in `compilePackage` in `src/core/catalog.ts`, and its license text into `resources/licenses/`. New icons are exported from `src/ui/icons.ts`.
13. **Agent guidance.** Describe when to choose the component in `plugins/showai/skills/design-presentation/references/reuse-selection.md`. Then run `npm run package:plugin`, which regenerates the Codex, Claude Code and Kimi copies of the Skills.

## Changing an existing built-in

To find the code of an existing built-in, start from its `registerBlock` call in `registry.ts`, which names the renderer and the validator. Saved pages keep the data they were written with, and exported pages keep the reader they were exported with. A change must therefore accept every shape the previous contract accepted, or convert old data when it is read; never tighten the contract in a way that makes existing pages fail validation. When the data contract, defaults or behavior change, raise `version` in `components.json`, update `propsSchema`, examples and documentation together, and extend the contract test with the old shape.

Agents learn the component from its documentation and examples, not from the source. After changing behavior, check that `usage`, the `recipes` and the examples still describe it, and update `reuse-selection.md` when the guidance on choosing the component changes.

## Verifying

Run the fast checks while you work, then the full set before opening a pull request.

```sh
npx vitest run src/components/builtin-registration.test.ts src/components/blocks/<contract>.test.ts
npm run check
npm run build
npm test
npm run test:component-gallery
```

`npm test` runs the catalog tests, which compile the editable source of every built-in and validate its defaults and examples against `propsSchema`, the documentation and the contract. It also renders every default and example in the CDN reader. Running a single file with `npx vitest run` needs `npm run build:portable` first, and tests that read `dist-agent` or `dist-runtime` need `npm run build`.

To measure inline readiness, run the readiness integration test and copy its result into `inline-readiness.json`:

```sh
SHOWAI_INLINE_READINESS=1 SHOWAI_INLINE_READINESS_OUT=/absolute/report.json \
  npx vitest run src/agent/inline-readiness.integration.test.ts
```

Then check the component in a development instance (see [Development and testing](development.md)). Insert it from the component menu, edit it, switch to reading view, reload, export the page with `export --format html` and open the file offline, and check a narrow window and the dark theme. A desktop-specific behavior needs the desktop instance; a browser result does not prove it. Note in the pull request which of these you checked.
