# 系统呈现规则：呈现设计稿

这一阶段把呈现规划变成具体画面。先确定环境，再设计整体布局，然后为每个部分写出视觉表达与交互方式。设计稿是制作的唯一依据，所以要具体到画面里有什么、怎样组织、彼此关系，详细程度接近图像生成的文本指令。

## 呈现环境

记录分辨率、长宽比和是否可交互。没有特殊要求时按电脑全屏、可交互阅读设计，以 1440×900 CSS 像素作为参考视口；实际宿主可能更窄，交付前核对。演示画面可用 16:9，长文自然纵向排布。需要静态导出或打印时，为每个交互部分设计静态替代。

## 整体布局

设计整份内容的阅读流：首屏、各部分的顺序、分区方式、导航与节奏。

- 首屏在参考视口内不滚动就能让读者明白这份内容从什么问题讲起、范围是什么，并看到一幅可理解的画面；读者需要先了解背景时，首屏就是背景与动机的第一幕，不放读者此时看不懂的结论或总览。不重复 Page 标题。
- 图文相邻：每个部分的说明放在它解释的图形旁边，不先铺多段背景再放一张图。
- 节奏：避免一两个交互区后接几大块连续正文；长章节按理解节点拆成图文相邻的片段。
- 对象身份稳定：同一个对象在不同部分使用同一名称、颜色与形状；颜色与文字、形状或线型共同表达状态。
- 窄视口重排图文和导航；必要的二维表图提供明确的滚动与总览方式。

## 每个部分的视觉表达

先按读者任务选表达形式，再查可用组件与素材。

| 读者任务           | 优先形式                                             |
| ------------------ | ---------------------------------------------------- |
| 认识对象与组成     | 原图、截图、剖面或标注示意；选择局部时就近解释       |
| 理解步骤与状态变化 | 流程、连续分镜、前后状态；对象身份保持，标出触发条件 |
| 理解机制           | 输入—作用—结果的关系图；可操作的参数让读者预测变化   |
| 比较与取舍         | 对照表、同尺度小多图、决策路径；共同口径，缺项可见   |
| 趋势、分布与异常   | 与数据语义匹配的图表；单位、样本、日期、原始值与来源 |
| 完成操作与排错     | 真实界面标注、步骤与分支；动作、反馈、恢复方式       |
| 探索与系统理解     | 总览与可定位局部；放大、筛选、详情与返回总览         |
| 核对论证或精确规定 | 有层次的正文、公式与原文；条件突出，图文相邻         |

图形的方向、空间、连接和尺度承担语义，装饰不能暗示没有证据支持的因果、比例或排名。图片可用真实素材，也可用图像生成工具制作；生成前写下必须保持准确的对象、数量、箭头与标签，生成后核对，精确数据与可操作对象保留为原生组件。

文字承担必要的辅助解释：标题直述主题；导语说明接下来看什么、用哪个例子、怎样操作；图注解释图中未讲清的概念与细节；要点说明看完应能回答什么。信息必须完整、准确、没有歧义。文字排布保证可读：桌面正文 18–20 px 起，标签与图注按渲染尺寸检查；用加粗、颜色标出重点与层级，同类含义用同一样式；固定字体体系，用留白、对齐和语义分组组织内容，空间不足时改结构而不是缩小字号。

特殊实体用悬停注释解释。读者可能不认识、但不值得打断正文去讲的实体——公式中的变量与记号、缩写、专有名词、特定用词——在出现处加注释：读者把鼠标移上去、用键盘聚焦或在触屏上轻点时显示一两句解释，正文保持连贯。写法在所有支持的文字位置相同：正文、表格、组件标题与说明、图表标签写 `[可见文字]{注释}`；公式里写 `\note{变量}{注释}`，只注释其中一个变量或同时注释多个；`[$公式$]{注释}` 注释整个公式。注释写清它是什么、形状或单位、取值或出处，可以含 `$…$` 公式。理解主线必需的定义与改变结论的条件仍写在正文，注释只做补充。

## 交互

每个交互写清初始状态、触发动作、状态变化、可见反馈与恢复方式（再次点击、Esc、重置）。默认状态是材料中的真实设定。交互只改变阅读焦点或临时参数，不改写事实。重要条件不能只放在悬停说明中。静态替代保留主线、关键状态与完整图注。

## 组件与素材选择

先确定表达形式，再在当前目录中查找真实能力：`catalog_list({kind:"component"})` 读取组件索引，模板组件来自 `template_context` 返回的固定引用。选用组件后读取其精确版本的 guide 与 parameters，按字段含义准备数据。顺序是：调整已有组件的数据与布局 → 组合已有能力 → 扩展已有组件 → 为确认的缺口新建组件。

## 设计稿的记录格式

每个部分写一幕（scene），对话中可以是一段具体描述；复杂作品追加到规划记录的 scenes 中：

| 字段           | 内容                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| id、nodes      | 场景标识；它解释的规划节点 id                                          |
| form           | 表达形式与所选组件或原生区块                                           |
| composition    | 画面中的对象、相对位置、箭头或尺度、准确标签、颜色、阅读顺序与文字落点 |
| visualReason   | 为什么这种表达能支持当前任务                                           |
| text           | 导语、图注与要点各写什么；哪些词加粗或着色                             |
| interaction    | trigger、change、reset；没有交互时省略                                 |
| static、narrow | 静态导出显示什么；窄于 640 px 时怎样重排                               |
| assets         | 真实素材来源或图像生成提示与核对要点                                   |
| check          | 读者看完这一幕应能完成的复述、判断或操作                               |

示例：暖白底，标题“同一个问题，两种输入布局”。上行是生成式模型的序列：[视频][问题] 后接逐个生成的时间 token，用灰色箭头表示逐步输出；下行是打分式模型：[视频][指令+问题][候选…][decide]，候选段用橙色，共享的视频段标“共享”。点击任一片段时，下方说明区显示该片段的作用，其他片段降低饱和度；再次点击恢复。图注解释“共享”意味着只计算一次。窄屏时两行改为上下堆叠并允许横向滚动。

“文字加关系图”“白底简洁”不能单独成为 composition。设计稿应让另一位制作者画出同一画面。制作完成后为每幕记录实现它的真实 blockIds，供评审校验。
