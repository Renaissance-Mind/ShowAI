# 系统呈现规则：呈现逻辑

这一阶段决定讲什么、按什么顺序讲、每一部分讲到多深。从读者当下的认知出发构建多级规划，产出呈现规划；设计稿阶段为规划中的每个部分决定画面。

## 第一级：整体逻辑与环节主题

先选择整体逻辑，再列出各环节的主题。常见逻辑：

| 读者任务 | 整体逻辑 |
| --- | --- |
| 理解一个方法、研究或论证 | 背景与动机 → 问题 → 机制 → 证据 → 条件与局限 → 自测 |
| 理解一个概念或系统 | 具体问题 → 对象与关系总览 → 关键过程 → 例子与反例 → 适用边界 |
| 作出选择 | 选择目标与标准 → 候选与可比事实 → 差异 → 取舍与条件 |
| 完成操作 | 前提与结果 → 步骤 → 预期反馈 → 异常与恢复 |
| 了解进展或现状 | 截止时间与结论 → 变化 → 依据 → 风险 → 待决策事项 |

每个环节写一句主题：读者读完这一段应当知道什么。第一级的顺序从读者当下的认知出发、层层递进：每个环节只依赖前面已经讲过的内容，读者顺着读下去不会遇到还没解释的结论、概念或数字。读者需要先了解背景才能看懂结论时（讲解论文、方法、研究或陌生概念），从任务背景与动机开始，不在开头放读者此时看不懂的总结或结论；只有读者已经掌握背景、只缺结论时（进展汇报、事实查询、标准已经明确的选择），才把结论放在最前。背景只讲后文需要的部分，不泛泛铺陈。

## 第二级：每个主题要讲清什么

为每个环节列出讲清主题所需的内容：必要定义、对象及其关系、过程或步骤、例子、反例、证据、成立条件。按读者简报判断哪些读者已经知道（直接使用）、哪些需要解释（展开）、哪些需要先澄清（提前）。

## 继续细化与停止

对仍然难以理解的概念或关系继续展开，直到叶子节点写出了具体的定义、过程、例子或条件。只写“介绍某概念”不算展开。每个分支在读者能完成对应任务时停止；各分支深度可以不同，不为统一层数填充内容。

共享的概念只解释一次，在使用处短释并指向原位置。改变结论或操作正确性的条件必须在主线中可见，不能只放进折叠或悬停说明。熟悉主题的读者可以从差异和证据直接进入，为他们标出快捷入口。

## 逐层检查

展开每一层时问三个问题：这一部分符合读者当前的认知吗；读者能据此理解吗；还需要进一步解释吗。回答“否”的部分调整顺序、补充先备概念或增加例子。

## 呈现规划的记录格式

对话中讨论提纲时可以写成缩进列表。复杂作品在制作前保存为规划记录（`presentation-plan.json`）。它的 nodes 是嵌套数组，每个节点含：

| 字段 | 内容 |
| --- | --- |
| id | 稳定标识，设计稿与评审引用它 |
| task | 读者读完这一部分能解释或完成什么 |
| answer | 这一部分的核心回答，一句话 |
| needs | 先备节点的 id |
| children | 下一级节点 |
| explanation | 叶子节点：准备讲清的定义、过程、例子或条件 |
| check | 用什么复述、判断或操作检查读者已理解 |

规划同时记录 reader、startingKnowledge、goal、cutoff 与 environment（width、height、interactive）。设计稿完成后在同一文件中追加 scenes。校验脚本只检查结构覆盖，不替代对内容的判断。

## 常见问题

先写完整长文再给每章附一张概括图；开头放了读者此时还看不懂的总结、结论或数字；后文才解释的概念提前出现；用抽象名词框图代替机制解释；证据条目代替需要展开的机制；关键条件只出现在脚注。发现这些问题时回到相应节点修改规划，而不是在设计稿里补救。
